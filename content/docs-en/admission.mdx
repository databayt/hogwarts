The admin admission flow runs from application review through enrollment confirmation. Confirming enrollment fires a single transaction that creates the Student, Guardians, FeeAssignments, and UserInvoices in one atomic step.

**Applying is always free.** The application wizard collects information only — no payment is taken at the application stage. Payment is triggered at two later points: the registration fee when the applicant accepts an offer, and tuition invoices after enrollment is confirmed.

## Student intake — four channels, one pipeline

A student can enter the system four ways. **All four funnel through one shared core, `provisionStudent`**, so however a student is added they get the same complete result — and every student is born from a real `Application`, tagged with the channel it came through.

| Channel         | How a student is added                                                             | `Application.channel` |
| --------------- | ---------------------------------------------------------------------------------- | --------------------- |
| Apply           | Family completes the public application, staff review → offer → confirm enrollment | `PORTAL`              |
| Admin single    | An admin creates one student in the `/students` wizard                             | `ADMIN_DIRECT`        |
| Onboarding bulk | CSV upload while setting up the school                                             | `ONBOARDING_IMPORT`   |
| `/school/bulk`  | CSV upload later, from the dashboard                                               | `BULK_IMPORT`         |
| Backfill script | Retroactive shadow application for a pre-unification student                       | `LEGACY_BACKFILL`     |

**A student who signs themselves up is not a fifth channel — they apply.** The
`internal-onboarding` and `newcomers` self-registration flows are for the adults
who join a school (teachers, staff, admins, parents); their `student` option was
removed, and a self-registering student is sent to `/{lang}/application` so they
enter the `PORTAL` pipeline like any other applicant. When a school has no open
campaign, the closed screen offers the inquiry form instead, and the family lands
in the **Leads** tab to be invited when admissions reopen.

The non-`PORTAL` channels create a "direct-admit" `Application` in the `ADMITTED` state, hung off a hidden per-school system campaign (named in the school's language). Everything below describes the `PORTAL` (public application → enrollment) path in detail; the other three channels reuse the same `provisionStudent` step from enrollment onward.

### Every channel is trackable

Whichever way a student arrived, the school can find their application and follow it:

- **Applications tab lists every channel by default.** A **Channel** column and facet filter (`?channel=PORTAL,BULK_IMPORT` — deep-linkable, multi-select, server-side) narrow back to the review queue. Until 2026-08-15 this tab hard-defaulted to `PORTAL`, so a direct-admit or imported student had a real application number that **no screen could look up**.
- **Student profile → application.** The unified profile sidebar shows the application number and links to the detail page (ADMIN/STAFF only — the detail page is RBAC-gated, so the link is not offered to viewers who cannot open it). Legacy students with no application (pre-unification, backfill not yet run) simply show no row.
- **Application → student.** The detail page shows the channel badge and, once a Student exists, a **View student profile** link — the loop closes both ways.
- **Direct admits are terminal.** `ADMITTED` has no outgoing status transitions and `confirmEnrollment` refuses an already-admitted application server-side, so surfacing these rows cannot double-provision anyone. Their detail page hides the offer/registration-fee rows (that ledger never runs for them) and says fees are billed through Finance → Fees like any enrolled student.
- **The Enrollment tab keeps its `PORTAL` default** — direct admits never pass through offer / registration-fee confirmation, so they have nothing to do there.

**Expect the legacy backfill to be visible.** Once `scripts/backfill-legacy-applications.ts` runs, every pre-unification student gains a `LEGACY_BACKFILL` row in the default view (~970 on the demo school). The filter is one click and lives in the URL.

### Keeping the invariant true

"Every student is born from an Application" only holds while every write goes through `provisionStudent`, and it is easy to break by accident — a new feature reaches for `db.student.create` and the student it makes is invisible to every surface that reads `Application.channel`. Two guards enforce it:

- **Lint** — a `no-restricted-syntax` rule in `eslint.config.mjs` rejects `*.student.create/upsert/createMany` outside a short, commented allowlist (`STUDENT_CREATE_ALLOWLIST`).
- **Test** — `src/tests/school-dashboard/listings/student-intake-invariant.test.ts` re-scans the tracked tree and imports that same allowlist, so an inline `eslint-disable` or a drifting config still fails CI. It also fails if an allowlist entry stops matching any file.

Legitimate exceptions are the core itself, the seeds, snapshot restore, ops scripts, and `createDraftStudent` — a wizard draft carries a non-null `wizardStep` and is deliberately Application-less until `completeStudentWizard` runs the core. As of the self-registration change above, that is the **complete** list: no intake path is exempt any more.

## Telling the family — one dispatcher, every channel

`provisionStudent` runs inside a caller-owned transaction and deliberately never notifies, so the telling happens after the commit. That work used to live inline in `confirmEnrollment`, which meant only `PORTAL` students were ever told anything: a student added through the wizard or a CSV import got a login, fees and invoices in silence, and so did their guardian.

`src/lib/student-provisioning-notify.ts` is that dispatch, shared by all five channels. It sends the student's account notice (with a password-setup link when the account is new), a `fee_due` notice covering the instalment schedule, and a guardian notice — falling back to the guardian's own address, since guardians made by `createOrLinkGuardian` are contact records with no login.

Two rules it must keep:

- **Placeholder addresses lose the email channel at row-creation time.** A student with no address of their own gets a synthesized `…@student.local`. Skipping only the inline send is not enough — the email cron skips recipients with _no_ address, and a placeholder is an address, so it would have tried to deliver later.
- **Bulk queues, single sends.** `delivery: "immediate"` sends inline so an admin who just clicked "Create" sees the mail land. A CSV import always passes `delivery: "queue"`, which writes the notification rows and lets the `process-email-notifications` cron drain them 50 at a time — a 500-row import spreads over hours instead of bursting. Bulk notification is **opt-in and off by default**; unchecked, an import stays as silent as it has always been.

## Nobody falls out of the flow

A student with no `academicGradeId` was the pipeline's quiet failure mode: `ensureStudentFeeAssignments` short-circuits on a null grade, so no fees were assigned, no invoices raised, and neither the `fee-due` nor the `fee-overdue` cron ever chased them. A CSV `section` column that did not parse was enough to cause it, and nothing surfaced the result.

The students list now has an **unplaced** filter (no grade **or** no class), and the daily `fee-due` cron alerts admins weekly while any remain. Setting a grade from the list re-runs the fee assignment and backfills what was missed.

Invoices and receipts are also delivered now, not merely generated: the fee notice states the instalment schedule and stamps `UserInvoice.sentAt`, and a cleared payment links the payer to their receipt.

Students that predate the unification are linked retroactively by `scripts/backfill-legacy-applications.ts`. It mints a `LEGACY_BACKFILL` shadow Application per orphan and sets only `Student.applicationId` — never the other eleven provisioning steps, which those students already have. Dry run is the default; `--execute` writes, `--school <id>` scopes to one tenant. It is idempotent: the `applicationId IS NULL` filter plus the column's `@unique` mean a re-run only picks up what is still unlinked.

## The journey, audited end to end (2026-08-15)

The whole path — apply → review → shortlist / reject → offer → the family's reply → registration fee → enroll → place in a section → tuition invoices → instalment reminders → payment → receipt — was traced across the admission, notification, finance and invoice blocks. The core money movement (fee assignment → invoices → allocation on payment → PAID/PARTIAL/OVERDUE) is sound; every break was at an edge. Fixed in that pass:

Still open — flagged, not fixed, each with its reason:

- **Instalment reminders and OVERDUE detection read only `FeeStructure.paymentSchedule`** (`fee-due` / `fee-overdue` crons). That JSON is populated only for auto-generated quarterly structures; a single-instalment or unscheduled admin-created fee has perfectly good `UserInvoice.due_date` values that neither cron reads — so it never reminds, never goes overdue, never accrues a late fee. The fix belongs in both crons (an invoice-due-date path). _Both files were mid-edit by another session on 2026-08-15._
- **Fee due dates and "today" windows are pure UTC** (`buildQuarterlySchedule`, `todayBounds`) — the same class of bug fixed in payroll; `src/lib/timezone.ts` has the helpers.
- **A withdrawn / archived student's open fees keep accruing fines and reminders** — the `archivedAt: null` filter was in flight in the other session's cron edits.
- ~~**No rejection reason**~~ — fixed 2026-09-04: a rejection or waitlist asks the reviewer for an optional note, stored on `reviewNotes`, carried in the family's notice and shown on the status tracker.
- **No refund path** (`PaymentStatus.REFUNDED` is displayed, never set) and **withdrawal does not void invoices** — feature work.
- **One parent account, two children** — `provisionStudent` reuses a Student by `userId`, and `@@unique([schoolId, campaignId, userId])` blocks a second application in the same campaign regardless of `allowMultipleApplications`. Needs a product decision on account model.
- **Purging a student** leaves `UserInvoice` rows orphaned (`feeAssignmentId` is `ON DELETE SET NULL`) and keeps the `User`.
- **Bulk section placement** exists only in the dictionary; placement is one row at a time.
- **`groupLabels` / `i18nGroupLabels` in every wizard config render no text** — `FormFooter` uses the array only for its length. Localizing them further is wasted until the footer renders labels.

Still open after this pass — product decisions and follow-ups, each with its reason:

- **One parent account, two children** (unchanged): `provisionStudent` promotes `Application.userId` from USER to STUDENT, so a parent who applied on their own account logs back in as their child, and `@@unique([schoolId, campaignId, userId])` blocks a second application in the same campaign (`submitApplication` already maps the collision to `APPLICATION_DUPLICATE`). Needs an account-model decision: a separate student User + the GUARDIAN role for the applicant.
- **Entrance / interview scheduling carries no date, time or venue** — the schema has no columns, so both statuses notify with the generic message. Needs `interviewAt` / `interviewLocation` (DDL) and a scheduling dialog.
- **No `EXPIRED` notice** to the family or the admin when the cron flips an unaccepted offer.
- **Tours**: no confirmation template exists for the family (only cancel / reschedule builders), and no day-before reminder.
- **Links built outside a request** (crons, webhooks) fall back to the primary root domain — a balqalam.com school's cron-sent links still carry `databayt.org`. Needs the school's root recorded on the `School` row.
- **Admission notification copy** lives in inline bilingual constants, not the dictionary / `NotificationTemplate` table — invisible to the tooling, unoverridable per school.
- **Registration fee materializes only at enrollment** (a `Payment` needs a `Student`): a cash fee confirmed for a family that later withdraws is never on the books.
- **`createJournalEntry` inside `confirmEnrollment`'s transaction uses the global client** — the ledger entry commits independently of the enrollment.
- **A started Stripe checkout is not expired** when the family switches to a manual rail.
- **An accepted-but-unpaid offer never lapses** — the price of the expiry fix: the cron exempts accepted offers, so a family that accepts and then never pays holds the seat until an admin withdraws it. Needs a payment deadline distinct from the acceptance deadline, with its own reminder and lapse.
- **WhatsApp / SMS** are unused by admission; instalment reminders and OVERDUE detection still read only `paymentSchedule`, in UTC (unchanged from 08-15).

## Enrollment transaction

`confirmEnrollment()` keeps the application-specific work (status guard, `ENR-{yy}-{seq}` enrollment number, the registration-fee `Payment` + ledger entry) and delegates the actual student creation to the shared **`provisionStudent()`** core (`src/lib/student-provisioning.ts`) — the same core the admin wizard and bulk import call. Inside one `db.$transaction`:

1. Set application status `ADMITTED` with the enrollment number.
2. `provisionStudent()`:
   - Resolve `AcademicGrade`, generate the per-school student code (`YYGGNNNN`).
   - Create `User` (role `STUDENT`) if the applicant was a guest; promote `USER` → `STUDENT` otherwise. **User is created before fees** — invoices no-op without a `userId`.
   - Create the `Student` (or reuse a wizard draft), linking `userId` + `applicationId`.
   - Match `applyingForClass` → `YearLevel`; create `StudentYearLevel` + set `academicGradeId`.
   - Auto-assign active `FeeStructures` → `FeeAssignment` rows (`PENDING`) and one `UserInvoice` per assignment (via `ensureStudentFeeAssignments` → `ensureInvoicesForAssignment`).
   - Create `Guardian` + `StudentGuardian` + `GuardianPhoneNumber`; copy application documents to `StudentDocument`.
3. Materialize the registration-fee `Payment` + journal entry when the registration fee was paid.

Post-transaction (best-effort, owned by the caller): notify student + guardians, mint a password-reset link for a new guest user, dispatch `fee_due` notifications, compute a section suggestion. The student is created with `wizardStep: null` and `status: ACTIVE`. The admin wizard and CSV import call `provisionStudent()` the same way (with `origin` `ADMIN_DIRECT` / `BULK_IMPORT` / `ONBOARDING_IMPORT`), which is what gives every channel the same login + invoices.

## Guardian auto-creation

For each parent (father, mother):

1. Split name into `firstName` + `lastName` (last space).
2. Upsert `GuardianType` (`father`, `mother`).
3. Create `Guardian` (or find by email).
4. Create `StudentGuardian` join row with occupation, `isPrimary`.
5. Create `GuardianPhoneNumber` if phone provided.

Father is primary; if no father, mother becomes primary.

## Section placement

After enrollment, place the student in a section:

- Enrollment response includes `suggestedSectionId` if exactly one section has capacity for the student's grade.
- Lists sections with available capacity for that grade.
- `placeStudentInSection()` assigns + auto-enrols in grade classes via `enrollStudentInGradeClasses()`.

## Wizard editing

Enrolled students can be edited via the student wizard (Students table → Actions → Edit). All application data is pre-populated.

`updateStudentWizardStep` only updates `wizardStep` for draft students (non-null `wizardStep`) — prevents accidental reversion of enrolled students. Final button reads "Save", not "Create".

## Merit list

Admins enter entrance and interview scores directly on the merit table (0–100 per score). `generateMeritList()` computes a weighted `meritScore` for each application:

- Entrance exam — 60%
- Interview — 40%

Applications are ranked by `meritScore` descending; unscored applications sort last. Scores are batch-written via `updateApplicationScores()`. The merit table covers shortlisted, selected, and waitlisted applications.

## Offer → accept → pay → enroll flow

Once an applicant is `SELECTED`:

1. An offer is created with a configurable expiry (`offerExpiryDays`, default 14).
2. The applicant logs in via a token'd offer URL (login preserves the full callback path).
3. The applicant pays the **registration fee** through the school's gateway (Tap for UAE/Gulf, Stripe elsewhere). The application wizard shows an informational payment preview — no payment is collected at the application stage.
4. On payment success, the admin sees a registration-fee paid banner and can proceed.
5. Admin clicks "Confirm enrollment" → `confirmEnrollment()` transaction fires (see Enrollment transaction).
6. Post-enrollment the admin uses the **Placement dialog** on the enrollment table to pick a section (seat counts shown); `placeStudentInSection()` enrols the student in all grade classes.

Abandoned-checkout retry is unblocked — applicants who navigated away can return and complete payment.

## Leads tab

The **Leads** tab (`/{lang}/admission/leads`) surfaces:

- **Inquiries** — contact form submissions with name, email, phone, interest grade, source, and follow-up status.
- **Tour bookings** — scheduled visits with attendee count, status (`PENDING` / `CONFIRMED` / `CANCELLED`), and reschedule/cancel actions.

ADMIN and STAFF roles have full action access; ACCOUNTANT has read-only access. New inquiries and bookings trigger in-app notifications to ADMIN + STAFF. Tour bookings guard against overselling (TOCTOU-safe) and honour the `enableTourBooking` campaign flag; cancel/reschedule decrements the attendee count correctly.

## Document-AI processing

Uploaded applicant documents (ID scans, transcripts) are processed by an extraction queue. The cron `/api/cron/process-document-jobs` runs every 10 minutes and drains pending jobs. `classifyDocument()` and `getDocumentProcessingStatus()` are RBAC-gated. AI usage is budget-checked (`canUseAI`) before each call; the bank-receipt Zod schema is optional so partial extractions do not fail the whole job.
