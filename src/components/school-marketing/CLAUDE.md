## Key Decisions

- **The zenda clone is bilingual and RTL as of 2026-08-08, and the mirror is GENERATED, not hand-written.** This supersedes the "English/LTR only" constraint recorded below for the homepage and `/about`; the three wrappers now take `dir` from the locale, and all 202 strings live in `marketing.site.home` / `marketing.site.about` (en + ar). `BASELINE_STATIC_GAP` is back to **0**. `/ar` measures 1.00 Arabic by character ratio, `/ar/about` 0.99. **Two passes in `scripts/scope-zenda.mjs`, and the split is the whole reason the sheet does not double in size:**
  - **Pass A logicalizes the BASE rule.** 1,282 physical declarations renamed to their exact logical twins (`margin-left` → `margin-inline-start`, and 20 more). This is a **no-op in LTR** — the two spell the same edge when direction is ltr — so `/en` renders byte-identically and RTL mirrors with no override at all. It also sidesteps what sinks the obvious approach: **an overlay that only ADDS `margin-right` leaves the base `margin-left` still matching under RTL, so the element gets both margins.** Renaming leaves no such residue. Verified declaration-by-declaration: 14,654 triples on both sides, identical.
  - **Pass B overlays what no rename can express** — 4-value shorthands, `translate()` offsets, `background-position`, `box-shadow`, `text-align`, `float` — under `.zenda-clone[dir="rtl"]`, which outranks the base by exactly one attribute selector, applied uniformly so the sheet's internal ordering is preserved. rtlcss does the flipping (devDependency, generation-time only). **The script THROWS if Pass B ever renames a property**, because that means a case Pass A missed and an overlay that would silently half-apply.
  - **Three traps, each of which cost real time and none of which is visible in the stylesheet:**
    1. **rtlcss does not touch `inset`.** Verified against 4.3: it flips `margin`, `padding`, `border-width/color/style` and `border-radius` shorthands and leaves `inset` alone. This sheet has **79 four-value insets** positioning nearly every decorative absolute, so the art would have stayed pinned while the layout mirrored. Pass A splits them into `inset-block` + `inset-inline` (which takes START then END — same box in LTR, mirrors free in RTL). Only the 4-value form; 1/2/3 values are horizontally symmetric.
    2. **Arabic typography follows the TOKEN, not the rule.** Zenda routes its type through `--_typography---font-styles--body`/`--heading`, both `"DM Sans"`, and the consuming rules read `var(…)` — so a literal-value test sees no face and skips them all. The first pass shipped an Arabic footer still set in DM Sans: `.zenda-clone` resolved to the Arabic face and `.body-v2` one level down put DM Sans straight back. Pass B now also rewrites any **custom property** whose value names a Latin-only face. Tracking goes to 0 in the same breath — zenda's `-0.04em` display ramp breaks Arabic letter joining.
    3. **A rule that PINS `direction` must not be flipped.** Zenda's Arabic terms blocks (`.rich-text-block-13..16`, beside `.arabic-tnc-section`) declare `direction: rtl` precisely because they hold Arabic on an otherwise-LTR site, and rtlcss dutifully flipped them to `ltr` — turning the one Arabic region on the page left-to-right. A pin is an instruction, not a layout artifact. Same principle already governs the academic marquee's `direction: ltr` track.
  - **`dir` must sit on the SAME element as `.zenda-clone`** — the overlay keys off `.zenda-clone[dir="rtl"]` and the base sheet's logical properties resolve against that element's own computed direction. Split them and the stylesheet and the layout engine disagree about which way the page runs.
  - **`zenda-shell.css` is hand-maintained and NEVER regenerated**, so the Arabic pass cannot see it. It needed its wordmark tracking zeroed by hand, and its one physical `margin-right: 0` had to become `margin-inline-end: 0` — in LTR both spell the same edge and it still won on order, but in RTL the base resolved LEFT while `margin-right` cancelled the right, so the -1.5rem pull came back on the other side. Keep it in step by hand.
  - **`scope-zenda.mjs` now carries a `LOCAL_OVERRIDES` list, and it exists because the generated sheet's "do not edit by hand" header was ignored.** `4e09f86ec` hand-edited `.section_services` to `background-color: inherit` so the feature-page showcase decks could show a themed background through (`.zenda-clone` shadows the app's whole token set, so a themed background has to be INHERITED from outside the scope). The first regeneration silently reverted it. Divergences from upstream live in that list now, each asserting the value it replaces so the script fails loudly if zenda changes underneath.

- **Motion is mirrored separately, because no stylesheet can reach it (2026-08-08).** GSAP writes `x` straight to `transform: translateX(…)` in physical pixels, so a card authored to slide in "from the left" kept doing so on a page running the other way, entering from the far side and crossing the content. `mx()` in `shared/rtl-motion.ts` negates an authored offset under RTL — 37 sites across the hero intro, benefits, features and cities timelines.
  - **Never apply it to a MEASURED value.** Anything from `getBoundingClientRect()` is already in the mirrored coordinate space, because the rect was measured after the mirror applied. The homepage intro's `logoToCentre` reads the logo's own rect and computes the distance to viewport centre — in RTL the logo starts at the right edge so the number comes out negative on its own. Negating it sends the logo the wrong way by exactly twice the distance. **Flip the numbers a human typed, never the ones the browser reported.**
  - The cities timeline is a third case: it animates the inset EDGES, not a translate, so `mx()` does not apply and its `from` state's physical `left`/`right` are swapped by hand. Unflipped, the "from" state is the side the pill already settles on and the sweep never happens.
  - **Checked and needing nothing:** the testimonials Swiper auto-detects RTL from the container (`swiper-rtl`, next slide moves left, peek on both sides), and the homepage marquee is entirely vertical (`y:` tweens), so direction does not enter into it.

- **`zenda-about/work.tsx` splits Arabic per WORD, not per character, and this is correctness rather than polish (2026-08-08).** Its scroll timeline tweens each `.char`'s colour, and the reference wraps every character in its own span. Arabic is cursive: a letter is shaped by its neighbours and only within one text run, so a span per character breaks every run and each letter falls back to its isolated form — the word stops joining up. **Measured on this page's own font: the same line renders 13.3% wider split per character and 0% wider split per word.** The width is only the tell; the damage is that the text reads as disconnected letters. The `.char` class stays on whichever unit it is, so `work-scroll.tsx` needs no change — the sweep advances a word at a time in Arabic, a letter at a time in English. **The test is on the SCRIPT, not the locale**, because a tenant's Arabic name can land on an English page.

- **The footer's links were remapped as part of the i18n pass, not after it (2026-08-08).** They pointed at zenda's own routes, every one a 404 on a school subdomain, and translating a label on a link that cannot resolve is not internationalization. Six inward destinations now, dictionary-keyed, sharing the nav's keys for the three routes both name — one translation per route, not two that can drift. **The three social links are deliberately NOT fixed and are a different class of problem:** unlike the 404ing columns they resolve, so they silently send a school's visitors to a competitor's Instagram. `School` carries `website`/`email`/`phoneNumber` but no social fields, so that needs a schema decision.
